# Phase 0 Research: Operator Console

**Feature**: `005-operator-console` | **Date**: 2026-06-13

Platform and kit patterns are settled (001–004). This is mostly composition;
the unknowns are the two new reusable pieces and how the example switches modes.

## R1. Mode + conversation models join engine-free kit state

**Decision**: Two engine-free modules — `intui/kit/state/modes.py`
(`ModeState`, `mode_slice()`, `mode_view`, `switch_mode_intent`) and
`intui/kit/state/conversation.py` (`ConversationEntry`, `conversation_slice()`,
`conversation_view`). Both join the layering guard + ruff ban. Components:
`intui/kit/mode_strip.py` and `intui/kit/conversation_log.py`.

**Rationale**: Same split as 002–004; reductions and selectors must be
headlessly testable (FR-012, SC-001/002).

## R2. Mode switching is intent → event → state (the capstone loop)

**Decision**: A `switch_mode` intent carries the target mode in its payload.
The application's intent handler appends a `mode_changed` event to the store
(exactly the `hello_replay` rerun pattern); `mode_slice` reduces it into the
current mode; `mode_view` re-highlights. No UI-only mode flag in the reduced
path (FR-011).

**Rationale**: Modes are in the requirements doc as both an event
(`mode_changed`) and derived state ("current mode"), with `switch_mode` as an
action. Routing through the loop is the point of the flagship — it shows the
whole contract working end to end. A convenience helper
`switch_mode_intent(name)` builds the intent so apps/commands don't hand-roll
payloads.

**Alternatives considered**: local UI mode state (simpler but bypasses the
contract the console exists to demonstrate — rejected for the flagship; other
apps may still keep mode local if they wish, since the model also accepts a
seeded initial mode).

## R3. ModeStrip and ConversationLog are BoundContainers

**Decision**: `ModeStrip(BoundContainer)` renders `mode_view` as a row of mode
entries, active one marked (e.g. `▸ Build`), and registers each mode's shortcut
through `IntuiApp.bind_key` (the app-global mechanism from 003) to post a
`switch_mode` intent. `ConversationLog(BoundContainer)` renders
`conversation_view` as a scrollable transcript, each entry prefixed with a
role/kind tag, auto-scrolled to the end.

**Rationale**: Reuses the 002 `BoundContainer` refresh contract and the 003
app-global key mechanism; nothing new in the foundation.

## R4. Per-mode layout via content switching in the example

**Decision**: The `operator_console` example owns a content area that shows
different kit components per active mode, driven by a `mode_view` subscription.
It uses Textual's `ContentSwitcher` (or equivalent show/hide) to swap mode
panes; the conversation surface and mode strip persist across modes. The store
composes all slices: `taskboard`, `artifacts`, `modes`, `conversation`.

**Rationale**: Per-mode layout is an app concern (spec assumption); the library
ships the model + strip + conversation, not a fixed console layout. Reusing the
engine's content switcher avoids reinventing pane management.

**Alternatives considered**: a generic library-level "console layout" widget
(premature — every app's mode layout differs; keep it in the example until a
second consumer proves the abstraction).

## R5. One recorded run drives everything

**Decision**: A committed `operator_console/recording.jsonl` interleaves
`message_added`/`question_requested`/`approval_requested`, `mode_changed`,
the task/lane vocabulary, a `diff_ready`, and an `evidence_ready` — a single
narrative the console replays. Generated by a committed-but-gitignored helper
pattern (write a temp generator, run, delete) as in prior features.

**Rationale**: One coherent run exercises every component and every mode
(FR-008), and keeps the example honest: it is real reduced state, not mock
widgets.
